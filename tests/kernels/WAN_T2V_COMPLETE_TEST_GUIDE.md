## Triton Kernel Tests

### What Are Triton Kernels?

**Triton kernels** are custom GPU code generated by PyTorch's TorchInductor compiler:

```python
# Original PyTorch (7 operations):
x = x + residual                    # aten.add
mean = x.mean(dim=-1, keepdim=True) # aten.mean
var = x.var(dim=-1, keepdim=True)   # aten.pow, aten.sum
normalized = (x - mean) / sqrt(var + eps)  # aten.div, aten.sqrt
output = normalized * weight + bias        # aten.mul

# Compiled (1 Triton kernel):
triton_red_fused__to_copy_add_mul_native_layer_norm_0(x, residual, weight, bias)
```

**Benefits:**
- Fuses multiple operations into single kernel (reduced memory bandwidth)
- Custom optimization for specific operation patterns
- Speedup: ~1.5-3× compared to eager mode

### Discovered Triton Kernels (17 Total)

#### 1. LayerNorm Kernels (8 kernels, 72 tests)

**Most Common Fusion in T2V**

**Kernel Names:**
- `triton_red_fused__to_copy_add_mul_native_layer_norm_*` (5 variants)
- `triton_red_fused__to_copy_pow_sum_view_*` (3 variants)

**ATen Operations Fused:**
```python
aten.add              # Residual connection
aten.mean             # Mean for LayerNorm
aten.pow              # Variance computation (x^2)
aten.sum              # Sum for variance
aten.div              # Division by sqrt(var)
aten.sqrt             # Sqrt(variance + eps)
aten.mul              # Weight scaling
# 7 operations → 1 Triton kernel (2-3× speedup)
```

**Test Coverage:**
- `test_layer_norm_standalone` - Basic LayerNorm (24 tests)
- `test_fused_add_layer_norm` - Add + LayerNorm fusion (24 tests)
- `test_variance_computation` - Variance calculation (24 tests)

**Example Test:**
```python
@pytest.mark.parametrize("batch_size", [1, 4])
@pytest.mark.parametrize("seq_len", [6, 16])
@pytest.mark.parametrize("hidden_dim", [2048, 5120])
def test_fused_add_layer_norm(batch_size, seq_len, hidden_dim, use_compile):
    x = torch.randn(batch_size, seq_len, hidden_dim, dtype=torch.bfloat16).to(DEVICE)
    residual = torch.randn(batch_size, seq_len, hidden_dim, dtype=torch.bfloat16).to(DEVICE)
    weight = torch.randn(hidden_dim, dtype=torch.bfloat16).to(DEVICE)
    bias = torch.randn(hidden_dim, dtype=torch.bfloat16).to(DEVICE)

    # Reference (eager)
    expected = WanT2VReferenceKernels.fused_add_layer_norm(x, residual, weight, bias)

    # Compiled (generates Triton kernel)
    impl = maybe_compile(WanT2VReferenceKernels.fused_add_layer_norm, use_compile)
    actual = impl(x.clone(), residual.clone(), weight, bias)

    torch.testing.assert_close(actual, expected, rtol=2e-2, atol=2e-2)
```

## Extern Operation Tests

### What Are Extern Operations?

**Extern operations** are direct calls to high-performance vendor libraries instead of generating Triton code:

```python
# TorchInductor generates:
extern_kernels.addmm(bias, input, weight, alpha=1, beta=1, out=output)

# Which calls:
# - OneMKL (Intel XPU)
# - cuBLAS (NVIDIA CUDA)
# - Intel MKL (CPU)
```

**Why use libraries instead of Triton?**
- **Performance**: 2-10× faster than Triton-generated GEMM
- **Hardware-specific**: Uses Tensor Cores (CUDA) or XMX engines (XPU)
- **Decades of optimization**: OneMKL (30+ years), cuBLAS (15+ years)
- **Production-tested**: Billions of workloads, numerical stability

## Test Strategy

### Dual-Mode Testing

Every test runs in **both modes** via the `use_compile` fixture:

```python
@pytest.fixture(params=[False, True], ids=["eager", "compiled"])
def use_compile(request):
    """Fixture to test both eager and torch.compile modes."""
    return request.param

def maybe_compile(func, use_compile: bool):
    """Conditionally apply torch.compile to a function."""
    if use_compile:
        return torch.compile(func, backend="inductor")
    return func
```

**Test execution:**
```python
def test_layer_norm(batch_size, hidden_dim, use_compile):
    # Reference (eager mode)
    expected = reference_layer_norm(x, weight, bias)

    # Compiled (generates Triton kernel or extern call)
    impl = maybe_compile(reference_layer_norm, use_compile)
    actual = impl(x.clone(), weight, bias)

    # Verify correctness
    torch.testing.assert_close(actual, expected, rtol=2e-2, atol=2e-2)
```

**Why test both modes?**
- **Eager mode**: Validates reference implementation correctness
- **Compiled mode**: Validates Triton kernel/extern operation correctness
- **Comparison**: Ensures eager/compiled parity (no bugs introduced by compilation)

### Precision and Tolerances

**Dtype:** `torch.bfloat16` (BF16)

**Tolerances:**
```python
torch.testing.assert_close(actual, expected, rtol=2e-2, atol=2e-2)
```

**Rationale:**
- BF16 has 7-bit mantissa (vs 23-bit for FP32)
- Compiled kernels may reorder operations (different rounding)
- Libraries may use different algorithms
- `rtol=2e-2` (2%) is appropriate for ML workloads

### Issue: Tolerance Failures

**Symptom:**
```text
AssertionError: Greatest relative difference: 0.025 at index (5, 305) (up to 0.02 allowed)
```

**Cause:** BF16 precision limitations or library differences

**Debug steps:**

1. **Check if consistent:**
   ```bash
   # Run test multiple times
   pytest tests/kernels/test_wan_t2v_kernels.py::TestLayerNormKernels::test_layer_norm_standalone -v --count=5
   ```

2. **Verify dtype:**
   ```python
   # In test, add:
   print(f"Input dtype: {x.dtype}, Expected dtype: {expected.dtype}, Actual dtype: {actual.dtype}")
   ```

3. **Check library versions:**
   ```bash
   python -c "import torch; print(f'PyTorch: {torch.__version__}')"
   python -c "import intel_extension_for_pytorch as ipex; print(f'IPEX: {ipex.__version__}')"
   ```

**If failures are consistent:** Tolerances may need adjustment for specific operations


**Fixes:**

1. **Run subset of tests:**


3. **Reduce test parametrization:**
   Edit test files to comment out large shapes temporarily

### Issue: Slow Test Execution

**Symptom:** Tests take much longer than expected (>10 seconds)

**Possible causes:**

1. **Kernel compilation overhead:**
   - First run compiles all kernels
   - Subsequent runs use cached kernels
   - Solution: Run tests twice, second run should be faster

2. **Large batch sizes:**
   - Tests with batch=8, seq=32 are compute-intensive
   - Solution: Filter to smaller configurations

3. **Library initialization:**
   - First GEMM call initializes OneMKL/cuBLAS
   - Solution: This is expected, only happens once

**Debug timing:**
```bash
# See slowest tests
pytest tests/kernels/ -v --durations=20
```
